# POS bug-fix and hardening log

> **Historical snapshot.** This 2026-10-10 log predates the move from Supabase to Cloudflare D1 and current barcode/receipt changes. Its SQL notes describe the old implementation and must not be treated as current D1 test results.

**Review date:** 2026-10-10 · **Scope:** code changes made during local QA/security review. No Supabase migration was executed and no production deployment was made.

| ID | Finding | Change made | Verification | Residual risk/status |
|---|---|---|---|---|
| ID-01 | `newId()` fell back to `Math.random()` when `crypto.randomUUID` was absent. | Use `crypto.randomUUID()` or a secure `crypto.getRandomValues()` UUIDv4 fallback; fail closed if no cryptographically secure RNG is available. | Unit test verifies RFC 4122 v4 format; typecheck/lint/build pass. | Browser/device CSPRNG was not tested on every target. |
| POS-01 | Daily receipt sequence used `localStorage` read/increment without transaction and did not include device identity; concurrent/local multi-device collisions were possible. | Move sequence allocation to a Dexie `appMeta` readwrite transaction and include a device suffix in receipt numbers. | 12 concurrent same-IndexedDB checkouts generated unique numbers; simulated device IDs yielded different suffixes. | This is not a real multi-device, cloud uniqueness or legal receipt-numbering test. Offline stores can still need cashier reconciliation. |
| PAY-01 | Two concurrent client confirmations could both read a pending digital order before either entered the stock transaction and deduct stock twice locally. | Re-read status, update payment/order and decrement stock within one IndexedDB readwrite transaction. | Two concurrent local confirmations produced one stock movement and one unit deduction. | Provider confirmation and SQL RPC were not exercised against a real Supabase/Paystack environment. |
| REF-01 | Refund eligibility, prior quantities and inventory writes were not enclosed in one transaction; duplicate product entries/concurrent refund requests and partial-rounding drift could over-refund. | Perform refund validation and writes inside one IndexedDB transaction; aggregate repeated product requests; track returned quantities; allocate the last partial refund the exact remaining gross/tax; block a new request while a prior provider reversal is unresolved. | Full/partial cash, `.333 + .667` quantity split, exact original gross/tax, duplicate full refund and inventory restoration tests passed. | SQL/RPC race tests and provider-side refund reconciliation were not run. Failed provider refunds require manager reconciliation; same returned quantity is not automatically refunded/restocked again. |
| REF-02 | Refund authorization had no configurable per-employee ceiling; previous UI-only manager guard was not enough. | Add `refundLimitMinor` to employee, owner-controlled editor/API, zero-deny/finite-cap/no-cap-owner rule, local helper, sync event authorization and Paystack refund-submission check. Status-only provider reconciliation is intentionally not gated by the current ceiling so an already-submitted refund can still be resolved. Add Supabase migration `004_employee_refund_limits.sql`. | Unit tests: zero limit denied, amount above ceiling denied, amount at ceiling accepted. Authenticated API behavior statically reviewed; unauthenticated local requests returned 401. | Migration must be reviewed/applied; cloud roles/limits were not tested with live Supabase Auth. All existing production users would default to zero until owner configures limits. |
| TAX-01 | A product-level tax override could replace an exempt/zero-rated/out-of-scope profile and charge tax contrary to the category treatment. | Apply product overrides only to standard-rated categories; validate quantity, minor-unit price, override and component ranges. | Inclusive/exclusive, compound, zero/exempt/out-of-scope, override and small-minor-unit tests passed. | Tax categories/rates remain illustrative and require GRA/accountant validation; no certified fiscal-device/E-VAT/CIS integration was tested. |
| PRIV-01 | Payment/receipt contact data had no explicit customer-purpose consent flow and no consent audit. | Add customer-agreement checkboxes, versioned `/privacy` template, authenticated `/api/privacy/consent`, minimized `privacy_consent_events` schema migration `003`, and server-side consent lookups before provider/email forwarding. | Next build/Cloudflare build pass; preview returned `/privacy` 200; unauthenticated consent request returned 401. | Migration/API were not exercised against Supabase. Notice still has merchant placeholders; customer agreement is cashier-attested. |
| SEC-01 | Next response security headers were absent. | Add `X-Content-Type-Options`, `Referrer-Policy`, `X-DNS-Prefetch-Control` and a Permissions-Policy preserving same-origin USB/Bluetooth while disabling unused camera/microphone/geolocation. | Local Worker preview response included expected headers. | No full CSP/HSTS, external origin review, TLS deployment, penetration test or browser permission audit was done. |
| UX-01 | Receipt email permission was conflated with other processing. | Require separate confirmation that the customer asked for an emailed receipt; keep PDF/share/print paths separate. | Component builds; no external email sent. | Resend configuration/delivery and opt-out/retention behavior are not verified. |
| DATA-01 | Local browser storage is unencrypted at application layer; backup/restore process was not established. | Documented device encryption, backup/restore, data-subject and release-gate procedures in separate reports; no encryption or backup implementation claimed. | Documentation added only. | **Open production blocker:** local IndexedDB at-rest encryption and a tested recovery path are not implemented. |
| SYNC-02 | Cloud-confirmed Paystack sales apply inventory deltas directly in `confirm_paystack_payment`; pending digital sales do not reserve stock and this function does not persist an inventory-review conflict when stock goes negative. | Identified by static SQL review; not patched because reservation/backorder and owner-resolution policy need a product decision plus real PostgreSQL concurrency tests. | Migration source inspection only. | **High-priority open risk:** concurrent paid digital orders can oversell; add durable review visibility and test in isolated Supabase before live money. |
| FEATURE-01 | Acceptance requires split tender, discounts and voids; current MVP has no corresponding transaction operations/UI. | Not implemented; explicitly excluded from passing counts and marked unavailable in QA matrix. | Source search and README scope review. | **Open product gap.** |
